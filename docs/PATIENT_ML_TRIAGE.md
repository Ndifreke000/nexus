# Patient ML Triage — how it works end to end

This documents the patient intake → ML triage feature end to end, across both
repos, for anyone picking up work in this area:

- **Backend**: [`Ndifreke000/nexus`](https://github.com/Ndifreke000/nexus) (this repo) — Rust/Axum API + the `ml-service` (Python/FastAPI).
- **Frontend**: [`NexusHealthAll/nexusApp`](https://github.com/NexusHealthAll/nexusApp) — the Patients page under `src/shared/patients/`.

It's split across two repos with independent deploys, which is how the two
sides drifted out of sync (see [History](#history--why-this-doc-exists)
below) — read that section before assuming "it's on main" means "it works."

## Data flow

```
Frontend (Add Patient modal)
   │  POST /api/v1/ingest/patient
   ▼
Rust backend: row inserted, status "pending", returns immediately (<100ms)
   │
   ▼
PatientPredictionWorker (background tokio task, polls every
PATIENT_PREDICTION_POLL_SECS seconds, default 2)
   │  picks up pending rows, calls ml-service
   ▼
ml-service (FastAPI, port 8001) — POST /predict/full
   ├─ diagnosis_model.pkl   (GradientBoosting)
   ├─ risk_model.pkl        (RandomForest + SMOTE)
   ├─ recommendation_model.pkl (drug, DecisionTree)
   └─ rule-based routing (urgency / route_to / department)
   │
   ▼
Result written back to `patient_predictions`, status "completed"/"failed"
   │
   ├─► broadcast on AppState.pipeline_events (tokio::sync::broadcast)
   │        │
   │        ▼
   │   GET /api/v1/pipeline/events (SSE) — pushed to the frontend instantly
   │
   └─► also readable via GET /api/v1/patients/{id} (poll fallback)
```

## Backend (`Ndifreke000/nexus`)

Relevant files:
- `src/handlers/patients.rs` — `ingest_patient`, `get_patient`, `list_patients`.
- `src/handlers/pipeline.rs` — `pipeline_events` (SSE).
- `src/repositories/patient.rs`, `src/repositories/patient_prediction.rs` — DB access.
- `src/services/patient_prediction_service.rs` — `PatientPredictionService` (issues predictions,
  emits `PipelineEvent`s) and `PatientPredictionWorker` (the poll loop).
- `src/services/ml_client.rs` — HTTP client to `ml-service`, configured via `ML_SERVICE_URL`.
- `src/utils/jwt.rs` — `extract_claims` (header-only) and `extract_claims_with_query_fallback`
  (header, falling back to `?token=` — needed for SSE, see below).

### Endpoints

| Method | Path | Auth | Notes |
|---|---|---|---|
| `POST` | `/api/v1/ingest/patient` | JWT header | Only `full_name` + `age` required; everything else defaults server-side. Queues a row, returns `{patient_id, prediction_id, status: "pending"}` immediately — no inline ML call. |
| `GET` | `/api/v1/patients` | JWT header | List, newest first, scoped to the caller's `hospital_id`. `?limit=` (default 50, capped 200). Each row includes its latest `prediction` (or `null`). |
| `GET` | `/api/v1/patients/{id}` | JWT header | Single patient + prediction. Used by the frontend's safety-net poll. |
| `GET` | `/api/v1/pipeline/events` | JWT header **or** `?token=` query param | SSE stream of `prediction_completed` / `prediction_failed` events, filtered to the caller's `hospital_id`. |

**Why the SSE endpoint takes a query param**: the browser's native `EventSource` API
cannot set custom headers, so it can't send `Authorization: Bearer <jwt>`. Both the
handler and the `require_role` middleware (for any route that uses it) accept the
token either way via `extract_claims_with_query_fallback` — header first, then
`?token=`.

### Config (`.env`)

```
ML_SERVICE_URL=http://localhost:8001
PATIENT_PREDICTION_POLL_SECS=2      # optional, defaults to 2
DATABASE_URL=postgres://...
JWT_SECRET=...
```

### ml-service (`ml-service/`)

Python/FastAPI, separate process on port 8001. Trained models live in
`ml-service/models/*.pkl` (generated by `train_models.py` from data produced by
`generate_training_data.py`). To run locally:

```bash
cd ml-service
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python train_models.py   # only if models/*.pkl don't already exist
uvicorn main:app --host 0.0.0.0 --port 8001
```

Every dropdown on the frontend intake form (`AddPatientModal.tsx`) is restricted to
the exact category values `generate_training_data.py` used (e.g. genotypes
`AA/AS/SS/AC`, severities `Mild/Moderate/Severe/Critical`) — the models were only
ever trained on these, so free text there would silently degrade predictions or hit
an unseen category in the one-hot encoders.

## Frontend (`NexusHealthAll/nexusApp`)

Relevant files, all under `src/shared/patients/`:
- `services/patientService.ts` — typed axios client (`PatientService.list/get/ingest`),
  types hand-mirrored from the Rust response structs.
- `hooks/usePatients.ts` — owns all list/SSE/poll state:
  - `loadPatients()` on mount → `GET /api/v1/patients`.
  - SSE subscription to `GET /api/v1/pipeline/events?token=<accessToken>` via the
    browser's native `EventSource`, patching predictions in place as events arrive.
  - An 8-second poll fallback (`GET /api/v1/patients/{id}`) for any row still
    `pending`/`processing` — covers a broadcast channel drop or a connection gap,
    since `tokio::sync::broadcast` has no replay buffer. Set well above the
    backend's own ~2s poll tick so it never contends with it.
  - `ingestPatient()` — posts, then optimistically prepends a synthetic row so the
    new patient appears instantly instead of waiting on a refetch.
- `components/AddPatientModal.tsx` — intake form, dropdowns locked to the ML
  training categories (see above).
- `components/PatientList.tsx` — the table: name/age/gender, symptoms, severity,
  **AI Triage** (risk badge + diagnosis) and **Recommendation** (drug + department)
  columns; shows an animated "Running AI triage…" state for rows without a
  completed prediction yet.

Routes: `/hospital/patients` (`src/routes/roles/hospital.routes.tsx`) and
`/medical-staff/patients` (`src/routes/roles/medical-staff.routes.tsx`), both
rendering the same shared `PatientList`. The hospital-admin sidebar has a nav entry
for it; the health-worker/medical-staff shell does not yet (known gap, not a
regression — see nexusApp PR #37).

## History — why this doc exists

The backend's ML pipeline has been added and reverted more than once:

1. `40dce27` — added the full pipeline, including `src/handlers/pipeline.rs` wired
   into the app.
2. `fbd8788` — reverted the whole feature (Render build was broken by an incomplete
   merge).
3. `9d22972` — re-added patient intake (ingest + get).
4. `ef2454e` ("fix: restore patient-pipeline module wiring") — restored
   `ingest_patient`/`get_patient` and their routes, but **did not** restore
   `pub mod pipeline;`, the `/api/v1/pipeline/events` route, or the
   `AppState.pipeline_events` wiring. `pipeline.rs` sat in the tree, fully written,
   but excluded from the build — `cargo check` compiled clean without it.

Meanwhile, [`nexusApp` PR #37](https://github.com/NexusHealthAll/nexusApp/pull/37)
shipped the frontend Patients page against the *intended* full API (list endpoint +
working SSE auth), and explicitly flagged both as backend dependencies "not
included in this PR — separate repo." Neither landed on `main` until
[this PR](https://github.com/Ndifreke000/nexus/pull/2), which:

- Adds `GET /api/v1/patients` (`list_patients` + `PatientRepository::list_by_hospital`
  + `PatientPredictionService::list_for_hospital`).
- Declares `pub mod pipeline;`, wires it into `app_routes.rs`, and adds
  `pipeline_events` to `AppState` (reusing the broadcast sender the worker already
  held — it just wasn't exposed for the route to subscribe to).
- Adds `extract_claims_with_query_fallback` for the SSE `?token=` param.

**Lesson for future changes here**: `src/handlers/patients.rs` and
`src/handlers/pipeline.rs` are two halves of one feature. Before assuming either
side works because the other repo's PR merged, check that the specific endpoint is
both declared in `handlers::mod` *and* registered as a route in
`routes/app_routes.rs` — a handler file existing and compiling in isolation proves
nothing.

## Running the whole stack locally

```bash
# 1. Postgres (see setup_local_db.sh for a scripted version)
#    DATABASE_URL in nexus/.env must point at it; migrations run automatically
#    on backend startup.

# 2. ml-service
cd nexus/ml-service && source .venv/bin/activate && uvicorn main:app --port 8001

# 3. Backend
cd nexus && cargo run   # listens on :8080 by default

# 4. Frontend
cd nexusApp && npm run dev   # :5173, VITE_API_BASE_URL=http://localhost:8080
```

Then log in as a `hospital_admin` (or `health_worker`) and open `/hospital/patients`
(or `/medical-staff/patients`).
